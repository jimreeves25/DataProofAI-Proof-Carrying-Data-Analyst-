# 1. CORE OBJECTIVE

Build a working **Proof-Carrying Data Analyst**.

The system must NOT behave like a normal chatbot that simply guesses an answer.

Its central principle is:

> **Every numerical answer must be backed by executable analysis code, an actual execution result, verification, and evidence. If the result cannot be reliably verified, the system must refuse to answer or re-plan the analysis.**

The system must handle messy real-world data including:

* CSV
* Excel
* JSON where practical
* Parquet
* multiple related tables
* missing values
* duplicate rows
* ambiguous dates
* unit mismatches
* conflicting data
* unsupported questions
* insufficient data
* misleading/trap questions

# 6. DATA INSPECTOR

Implement:

```text

```

Its job is to inspect every uploaded dataset BEFORE the AI generates code.

For each file determine:

* format
* number of rows
* number of columns
* column names
* inferred data types
* sample rows
* missing-value counts
* duplicate-row count
* unique-value counts where useful
* numeric ranges
* date-like columns
* possible currency/unit columns
* suspicious columns
* relationships between tables where detectable

For example:

```json

  "rows": 1500,

  "missing_values": {
    "revenue": 12
  },
  "duplicates": 5
}
```

The inspector should NOT ask the LLM to perform basic deterministic statistics that Python can calculate itself.

Use Python for deterministic inspection.

# 8. AI AGENT

Create:

```text
backend/app/agents/analyst_agent.py
```

The agent receives:

```text
User question
+
DataProfile
+
available datasets
+
previous failed attempt, if any
```

Its responsibility is to determine:

1. What is the user asking?
2. Which datasets are relevant?
3. Which columns are required?
4. What calculations are required?
5. Are there ambiguities?
6. Are there missing values?
7. Are there unit mismatches?
8. Are there contradictory sources?
9. Can the question actually be answered?
10. What analysis plan should be used?

The agent should output a structured plan.

Example:

```json
{
  "answerable": true,
  "reason": null,
  "datasets": ["sales.csv", "expenses.csv"],
  "operations": [
    "filter Q2 records",
    "aggregate revenue",
    "aggregate expenses",
    "calculate profit margin"
  ],
  "required_columns": [
    "date",
    "revenue",
    "expense"
  ]
}
```

If the question is clearly unanswerable:

```json
{
  "answerable": false,
  "reason": "Expense data is missing for Q2."
}
```

In that case DO NOT generate code.

Return a controlled refusal.

```python
print(result)
```


# 13. VERIFIER

Create:

```text
backend/app/verifier/verifier.py
```

This is one of the MOST IMPORTANT components.

The verifier must NOT simply ask the LLM:

> "Is this answer correct?"

That would defeat the purpose.

Use deterministic checks wherever possible.

Verify:

### Execution

Did the generated code actually run?

### Output

Did it produce the expected result?

### Data consistency

Check:

* missing required values
* duplicates
* incompatible types
* invalid dates
* suspicious units
* conflicting values

### Reproducibility

Can the same calculation produce the same result again?

### Expected result type

If expected:

```text
number
```

don't accept:

```text
random prose
```

### Numerical consistency

Where practical, independently recalculate the final numerical result.

For example:

```text
Generated result:
53.33

Independent verifier:
53.33

Difference:
0.00

PASS
```

```text
Original question
+
Original data profile
+
Previous analysis plan
+
Previous generated code
+

+
```

Then it creates a new plan.

Example:

```text
Attempt 1:
Used revenue column incorrectly.

FAIL — selected column is gross revenue, not net revenue.

↓

REPLAN

Attempt 2:
Use net_revenue column.

↓

Execute

↓

Verify

↓

PASS
```

This should be visible in the internal execution trace.

# 17. REFUSAL ENGINE

The system must know when NOT to answer.

Examples:

### Missing data

```text
Question:
"What was profit in April?"

Revenue exists.
Expenses missing.

→ REFUSE
```

### Unit mismatch

```text
Revenue:
USD

Cost:
EUR

No conversion information.

→ REFUSE
```

### Contradictory sources

```text
sales.csv:
Revenue = 50,000

report.xlsx:
Revenue = 60,000

No source priority.

→ REFUSE / REQUEST CLARIFICATION
```

### Ambiguous question

```text
"What were sales last quarter?"

Multiple possible date definitions.

→ ASK FOR CLARIFICATION
```

The system must prefer:

```text
"I cannot determine this reliably from the supplied data."
```

over a fabricated answer.
